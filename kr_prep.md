# Подготовка к КР №1

## Когда я выберу rebase, а когда merge? Почему?
- **rebase** — для своей локальной/личной feature-ветки, которую ещё никто не забрал: подтянуть свежий `main` (`git rebase main`) и причесать коммиты (`rebase -i`) перед PR. История получается линейной, ревьюеру проще читать.
- **merge** — для интеграции в общую ветку (`main`, `develop`) и для веток, с которыми работают другие: merge не переписывает существующие коммиты, сохраняет факт параллельной разработки и безопасен для публичной истории.

## Что произойдёт, если сделать rebase публичной ветки, с которой работают коллеги?
Rebase создаёт новые коммиты с новыми хешами (D → D'). Чтобы отправить их, придётся делать `push --force` — на сервере старые коммиты заменятся новыми. У коллег локально останутся старые D, E: при `git pull` Git увидит две расходящиеся истории, появятся дубли коммитов, лишние merge-коммиты и конфликты, а при неаккуратном force-push можно затереть чужие коммиты, запушенные в промежутке. Поэтому правило: never rebase public branches.

## Зачем нужен multi-remote и в каких реальных сценариях он применяется?
Multi-remote — это несколько удалённых репозиториев у одного локального. Сценарии:
- **Форк + upstream**: `origin` — свой форк, `upstream` — оригинал; из upstream подтягиваем обновления, в origin пушим свои ветки и делаем PR.
- **Зеркало/бэкап**: основной репо на GitHub, копия на GitLab/Gitverse — на случай блокировки или недоступности платформы (актуально для РФ).
- **Разные среды/команды**: внутренний GitLab компании и публичный GitHub для open-source части; деплой через push в remote хостинга (Heroku, Dokku).
